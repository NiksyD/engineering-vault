# Delta-Based Background Sync Engine

## 1. Overview & Problem Statement
A major pain point in mobile education apps is forcing users to wait for a 50MB question database download on every app launch. Furthermore, Philippine tax laws and accounting standards change constantly (e.g., CREATE Act amendments, Ease of Paying Taxes Act [RA 11976], BIR Revenue Regulations).

The **Delta-Based Background Sync Engine** operates on a **Local-First / Offline-First** paradigm:
1. All user writes (exam attempts, flashcard reviews, notes) write immediately to a local Write-Ahead Log (WAL) table.
2. Downstream syllabus updates and errata patches download as tiny delta packets (diffs) rather than re-downloading whole question databases.
3. Upstream telemetry syncs quietly to Supabase PostgreSQL when internet connectivity is detected, without blocking the user.

---

## 2. Sync Topology & Architecture

```
                    ┌────────────────────────┐
                    │    Flutter Local App   │
                    └───────────┬────────────┘
                                │ (Instant local writes)
                                ▼
                    ┌────────────────────────┐
                    │   Local Write Queue    │
                    │      (WAL Table)       │
                    └───────────┬────────────┘
                                │ (Background Sync Worker)
                                ▼
                     [ Network Available? ]
                     ├── NO  ──► Stay Offline (0ms lag, no errors)
                     └── YES ──► Supabase PostgreSQL Sync Manager
                                     │
                   ┌─────────────────┴─────────────────┐
                   ▼                                   ▼
        [ Upstream Push ]                     [ Downstream Delta Pull ]
   - Exam score logs                     - Errata question corrections
   - SRS flashcard metrics               - New Philippine tax law patches
   - Sync status updated to synced       - Schema version check
```

## 3. Downstream Delta Patching (Tax Law & Errata)
Instead of replacing entire test banks, the server publishes timestamped delta records:

```json
{
  "sync_version": 1042,
  "timestamp": "2026-10-28T12:00:00Z",
  "mutations": [
    {
      "op": "UPDATE",
      "entity": "ExamQuestion",
      "id": 44,
      "diff": {
        "statutoryBenchmark": "CREATE ACT (RA 11534) & EOPT (RA 11976)",
        "standardRationale": "Updated for revised 2024 filing deadlines and MSME thresholds."
      }
    },
    {
      "op": "INSERT",
      "entity": "ExamQuestion",
      "record": { "id": 501, "subject": "TAX", "topic": "EOPT Act Withholding Changes", "..." : "..." }
    }
  ]
}
```

## 4. Upstream Sync & Conflict Resolution
- **Strategy:** Last-Write-Wins (LWW) with client-side monotonic timestamps, or append-only event logs for attempts.
- **Privacy Mode:** Examinees can toggle **"Strict Offline Mode"** in settings to prevent their performance analytics from ever leaving their physical device.

---

## 5. Engineering Constraints & Edge Cases
- **Background Execution in Flutter:** Utilize `workmanager` on Android or a background sync isolate. Must respect Android Doze mode and never wake the device aggressively.
- **Transaction Idempotency:** Every sync packet generated by the client has a unique `uuid_v4` transaction ID (`tx_id`). Re-sending a dropped packet to Supabase is a safe, idempotent upsert.
